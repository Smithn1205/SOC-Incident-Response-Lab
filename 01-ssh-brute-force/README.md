# Incident 01 — SSH Brute-Force Detection & Investigation

## Status

**Investigation complete — sanitized evidence upload pending.**

> **Lab scope:** This incident was intentionally simulated in an Azure environment owned and controlled by the author. It does not represent a production security incident.

## 1. Incident Summary

A controlled burst of repeated SSH authentication attempts was generated against an Ubuntu VM and investigated in Microsoft Sentinel. Eight attempts targeting the invalid account `wronguser` were observed from a single controlled source within approximately 2.6 seconds.

The activity exceeded the lab detection threshold of five failed attempts. A follow-up search found no successful SSH authentication after the failure burst.

**Classification:** Simulated true positive — unsuccessful SSH brute-force-style activity.

**Impact:** No evidence of successful account access.

## 3. Log Sources

The investigation used Linux authentication events generated by OpenSSH and collected through the following pipeline:

```text
Ubuntu SSH authentication logs
        ↓
Linux Syslog (auth / authpriv)
        ↓
Azure Monitor Agent
        ↓
Data Collection Rule
        ↓
Log Analytics workspace
        ↓
Syslog table
        ↓
Microsoft Sentinel / KQL
```

The DCR collected the `auth` and `authpriv` facilities at `Info` severity and higher.

Before generating attack traffic, a harmless marker (`SOC-LAB-CHECKPOINT-2`) was successfully observed in the `Syslog` table. This verified end-to-end log ingestion before the detection test began.

## 4. Detection Hypothesis

A single source generating multiple failed SSH authentication attempts against the same host within a short period may indicate brute-force or automated account-guessing activity.

For this controlled lab, the detection threshold was set to **5 or more failed attempts within the query window**. This is a demonstration threshold and should be tuned against normal authentication behaviour in a production environment.

## 5. Detection Query

The validated query is stored in [`detection.kql`](./detection.kql).

The query:

1. searches recent Linux `Syslog` events,
2. limits results to the lab host and `sshd` process,
3. identifies `Invalid user` authentication events,
4. extracts the source IPv4 address and targeted username,
5. counts failures by source, user, and host,
6. records the first and last observed timestamps, and
7. returns groups with at least five failures.

## 7. Investigation Steps

### Initial Triage

A Sentinel search of `Syslog` events from `soc-linux-01` showed repeated messages in the form:

```text
Invalid user wronguser from [REDACTED_SOURCE_IP] port <ephemeral-port>
```

Eight such events were recorded in rapid succession.

### Source and Account Analysis

The detection query grouped the events by source IP, targeted account, and computer. All eight authentication failures originated from the same controlled source and targeted the same nonexistent account, `wronguser`.

The repeated pattern and short duration were consistent with the intentionally generated brute-force-style test activity.

### Successful-Login Correlation

A second KQL query searched for OpenSSH messages beginning with `Accepted` after the failed-login sequence began.

**Result:** No successful SSH authentication was found after the burst of failed attempts.

### Analyst Assessment

The detection correctly identified the simulated activity. The attempts did not result in authenticated access, so there was no evidence of compromise.

Because the traffic was deliberately generated from an analyst-controlled system, the incident is classified as a **simulated true positive** rather than a real malicious event.

## 9. MITRE ATT&CK Mapping

**T1110 — Brute Force**

The activity consisted of repeated SSH authentication attempts against an account in a short period. The high-level Brute Force technique is used here because the lab demonstrated repeated authentication attempts rather than a confirmed password-compromise scenario.

## 10. Containment / Remediation

If similar activity were observed in a real environment, appropriate actions would include:

- verify whether the source IP is expected or trusted,
- determine whether any successful authentication followed the failures,
- keep SSH password authentication disabled where operationally feasible,
- require key-based authentication,
- restrict SSH exposure using NSGs/firewalls and trusted source networks,
- review the targeted account and host for subsequent suspicious activity,
- consider rate limiting or automated blocking for repeated failures,
- tune alert thresholds to the organisation's normal authentication behaviour.

In this lab, SSH remained restricted to the analyst's `/32` public IP and password authentication remained disabled.

## 11. Conclusion

Microsoft Sentinel successfully ingested the Ubuntu SSH authentication events and the KQL detection identified eight repeated invalid-user attempts from one source within approximately 2.6 seconds.

No successful SSH authentication was observed after the failure sequence. The activity was therefore assessed as a **simulated true positive with no evidence of account compromise**.

## 12. Lessons Learned / Detection Improvements

- Validate the complete logging pipeline before generating attack traffic. A known Syslog marker made it possible to prove that Linux logging, AMA, the DCR, Log Analytics, and Sentinel were working end to end.
- Avoid double-counting related SSH messages. Filtering specifically for messages beginning with `Invalid user` prevented associated `Connection closed` events from inflating the failure count.
- A restrictive firewall rule does not help if a broader allow rule still permits the same traffic. During setup, a broad SSH allow rule was identified and removed after reviewing the effective NSG rules.
- A failure threshold alone is not enough for production detection. Future versions could add time-window binning, multiple targeted usernames, source reputation, geolocation, and correlation with successful authentication.
- Investigation should not stop at counting failures. Checking for a subsequent successful login is essential for determining whether repeated attempts resulted in compromise.
